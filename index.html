SOP 01

Navigate vCenter & Read Your Inventory

Your orientation runbook: log in, understand what you're looking at (inventory, health, networking, storage), and — just as important — know what NOT to touch.

Env: FMLBCUAccess: vCenter (read/operate)~10 min

Get in & get oriented

Log in to vCenter
☞
Do thisBrowser → https://vcenter-fmlbcu.example.com/ui → sign in with your SSO/AD account.

You land on the Summary for vCenter itself. The hamburger menu ☰ (top-left) opens the big areas; the left tree is your inventory.

Learn the four inventory views

Near the top-left are four ways to look at the same environment. Click each once so you know where things live:

Hosts & Clusters
The physical side — your cluster and its two ESXi hosts. Where you do maintenance/upgrades.
VMs & Templates
The VMs and your golden-image templates, organized in folders.
Storage
The datastores and their free space.
Networking
The distributed switch and its port groups (the VLANs).
Read the inventory tree top-to-bottom

Expand it: vCenter → Datacenter → Cluster → Host → VM. That nesting IS the environment — a VM runs on a host, hosts live in a cluster. Find the boxes you're responsible for.

Read the health & state

Check a host's health
☞
Do thisClick a host → Summary

Look for: connection state (Connected, not Disconnected/Maintenance), any red/yellow alarms, and CPU/Memory usage. Then Monitor → Tasks & Events shows what's been happening on it.

Check a VM's state
☞
Do thisClick a VM → Summary

Confirm Power state (On), the IP and VMware Tools: Running (if blank, Tools isn't installed), and check Snapshots — old ones are a red flag.

Read the networking & storage

Understand your networking
☞
Do this☰ Menu → Networking → expand the Datacenter → your Distributed Switch (vDS)

Underneath the vDS are the port groups — each is a network/VLAN a VM can plug into (e.g. a trunk like 2211). To see which network a VM is on: VM → Summary (or Edit Settings → Network adapter). A VM on the wrong port group is on the wrong network — a top cause of "it can't talk to anything."

What you're readingvDS-FMLBCU ├─ Mgmt (VLAN 100) ├─ Trunk-2211 (VLAN trunk 211–213, static binding) └─ Uplinks (the hosts' physical NICs → the real network)
Check storage headroom
☞
Do this☰ Menu → Storage → click each datastore → check Free

A full datastore freezes every VM on it (and snapshots grow into this space). Note which datastore your VMs live on.

Glance at Recent Tasks before you leave

The bottom Recent Tasks pane shows who did what, to what, and whether it worked — your accountability trail. Get in the habit of reading it.

What to do & what NOT to do

✓ DO

  • Check alarms first, every time.
  • Work one host at a time; confirm the other has capacity.
  • Use the Web Console as your lifeline when SSH is dead.
  • Snapshot before a risky change; delete it after.
  • Log changes in change control.

✕ DON'T

  • Don't rename/delete port groups, the vDS, or uplinks — you'll cut VMs off the network.
  • Don't "Delete from Disk" a VM (that erases it — use Power Off).
  • Don't remove a datastore that has VMs on it.
  • Don't power off a host without maintenance mode.
  • Don't take both hosts down at once.

▸ The mindset

Day one is for reading, not changing. If you're not sure what a control does, don't click it — ask, or look it up. Most vCenter damage is a confident wrong click.

SOP 02

Create a Golden-Image Template From Scratch

The full runbook: download RHEL from Red Hat, carry it across, build and harden one VM, generalize it, and turn it into the template in vSphere that every future server is stamped from.

Start: Red Hat websiteEnd: template in vSphere~2–3 hrs

Get the RHEL image from Red Hat

Go to the Red Hat download site & sign in
☞
Do this (on an internet-connected machine — the low side)Browser → access.redhat.com → Log In with your Red Hat account → Downloads → Red Hat Enterprise Linux.
Pick the version, and download the RIGHT file

Choose the RHEL version (e.g. 9.x), architecture x86_64. You'll see a few file types — here's which to grab and why:

Binary DVD ISO ← use this
The full installer. You boot a blank VM from it and install RHEL fresh. This is what you want to build a template from scratch.
Boot ISO
A tiny installer that pulls packages over the network — not ideal air-gapped.
KVM Guest Image (.qcow2)
A pre-built cloud disk for KVM — wrong hypervisor, skip.
VMDK / OVA
A pre-built disk/appliance for VMware. You could import one instead of installing, but for a hardened baseline you control, installing from the DVD ISO is the standard path. (Building a VMDK yourself with Image Builder is the alternate route — see the note at the end.)

▸ ISO vs VMDK in one line

An ISO is an installer you boot and install from. A VMDK/OVA is an already-built disk you import. From scratch = ISO.

Carry it across the air gap
Fill in — your site's procedureCopy the ISO to [your approved media — e.g. write-once optical / approved USB], move it across [per your cross-domain / media-transfer SOP], and place it on [the high-side share / ISO library]. Do not skip your scanning/approval steps.

Build the base VM

Upload the ISO where vSphere can mount it
☞
Do this☰ Menu → Storage → pick a datastore → Files → Upload Files → select the ISO. (Or add it to a Content Library.)
Create a new, blank VM
☞
Do thisRight-click the cluster → New Virtual Machine → Create a new VM.

Name it like a template (e.g. tmpl-rhel9-base), pick the datastore, choose Guest OS = Red Hat Enterprise Linux 9 (64-bit), and size it to your baseline (CPU/RAM/disk). On the CD/DVD drive, choose Datastore ISO File and point it at the ISO from step 4; tick Connect at power on.

◆ Template networking — read this

Set the VM's network adapter to a safe, non-production port group for now (a management or isolated/"staging" network) — not a live production VLAN. A freshly-built, not-yet-hardened box should never boot straight onto production. The real network + IP get chosen per-deploy (SOP 03). See the recommendation at the end of this runbook.

Install RHEL from the ISO

Power on → open the Web Console → step through the installer: partitioning (LVM), root password, an admin user, timezone. Or feed it a Kickstart for a hands-free, identical build every time.

You'll end up withA running RHEL VM at the login prompt, on your staging network.

Configure & harden the baseline

Make it the way EVERY server should start

Log in and set your baseline. This is what makes it "golden":

# register to Satellite + patch to current subscription-manager register --org="FMLBCU" --activationkey="rhel9-key" dnf -y update # install your standard agents/tools, set baseline configs (time, etc.) dnf -y install open-vm-tools your-standard-packages systemctl enable --now vmtoolsd chronyd

Then harden it to STIG (run your SCAP remediation — that becomes SOP 07). Everything you bake in here, every future box inherits.

Generalize it (strip the unique identity)

If you skip this, every clone is an identical twin and they'll fight on the network. Run this last, right before templating:

truncate -s 0 /etc/machine-id # unique ID regenerates on next boot rm -f /etc/ssh/ssh_host_* # each host makes its own SSH keys subscription-manager unregister # deploys re-register themselves dnf clean all rm -f /root/.bash_history poweroff
You'll end up withA powered-off, hardened, identity-cleared VM — ready to become the master.

Turn it into the template

Convert the VM to a template
☞
Do thisRight-click the powered-off VM → Template → Convert to Template.

It now appears under VMs & Templates with a template icon and can't be powered on — that's correct. This is the master image; you never run it, you stamp copies from it.

Confirm it's your pull-from source

From now on, launching that server = right-click this template → New VM from This Template (that's SOP 03). Keep it patched by periodically converting it back to a VM, updating, and re-templating.

Done — you now havetmpl-rhel9-base (Template) ← the golden image every RHEL 9 box is built from

About the template's network (the recommendation you asked for)

You had a good instinct that it should basically be "blank." Here's the enterprise best practice and the options:

No fixed IP in the template
Never bake a real IP/hostname into a template — every clone would collide. Identity is set per-deploy with a Guest Customization Spec (SOP 03).
Adapter on a staging/isolated port group (recommended)
Point the template's NIC at a safe, non-production network so a fresh, unhardened clone can't touch production before you've finished it. You then move it to the real VLAN at deploy.
Choose the real network at deploy
The deploy wizard lets you pick the correct port group and apply a Customization Spec — that's where the "real" networking is decided, per VM.

✓ Recommended pattern

Template: NIC on a staging/isolated port group, no fixed IP, VMware Tools installed, hardened. At deploy: pick the correct production port group + apply a Customization Spec for hostname/IP/DNS. Best of both — safe master, correct per-box networking.

▸ Alternate path: Image Builder

Instead of installing from the DVD ISO, you can define the image as code with RHEL Image Builder (composer-cli) and output a .vmdk/.ova, then import that into vSphere and convert to a template. Same destination; use it when you want the image rebuilt automatically from a recipe.

SOP 03

Deploy a VM From the Template — the Secure Way

The enterprise runbook for stamping out a new server from your golden image: correct network, unique identity, and a proper first-boot shakedown before it's trusted.

Start: golden templateEnd: hardened, enrolled server~20 min

Before you click

Gather the facts for this new box

Know these before you start, so you're not guessing mid-wizard:

Name & purpose
Hostname and what it's for (drives folder + naming).
Network
Which port group / VLAN it belongs on, plus its IP, mask, gateway, DNS.
Placement
Which host/cluster, and which datastore (with room).

Confirm the template is current (patched/hardened). If it's stale, update it first.

Deploy it

Start the deploy from the template
☞
Do thisRight-click tmpl-rhel9-base → New VM from This Template.
Name & folder

Enter the new server's name and pick the folder it lives in.

Pick compute

Choose the host or cluster it should run on. Let DRS place it if you're unsure.

Pick the datastore (storage)

Choose a datastore with free space; set the disk to Thin if that's your standard. The template's disk is copied here, so it needs room.

✕ Don't pick a near-full datastore

The copy will fail, or the VM will freeze later. Check Free space first.

Pick the CORRECT network (not staging)

On the Select networks screen, set the adapter to the real production port group / VLAN this box belongs on — this is where you move it off the template's staging network.

Apply a Guest Customization Spec (the secure, repeatable part)

Tick Customize the operating system and pick your Linux spec (build one under Policies and Profiles → VM Customization Specifications). It sets a unique hostname, IP/DNS, and domain on first boot — so the clone comes up as its own machine, not a copy of the master.

▸ Why this is the enterprise way

No two boxes collide, no manual reconfig, and it's repeatable/auditable. Hand-editing IPs after deploy is how duplicates and mistakes happen.

Review & Finish → power on

Check the summary, Finish, and power it on. Watch it in Recent Tasks.

First-boot shakedown (before you trust it)

Confirm it came up as its OWN machine
hostnamectl # its new hostname (not the template's) cat /etc/machine-id # a NEW id (regenerated) ✓ ip -br a # its own IP from the customization spec
Good = unique identityStatic hostname: web05.example.com ens192 UP 10.1.1.55/24 ← its own IP, not the master's ✓
Register, patch, enroll, verify

Bring it into the fold and shake it down:

subscription-manager register --org="FMLBCU" --activationkey="rhel9-key" dnf -y update ipa-client-install --mkhomedir --server=idm.example.com --domain=example.com ss -tulpn # what's listening? close anything unexpected systemctl --failed # nothing broken?

Then re-run/confirm STIG hardening. Only after this is the box ready for its job.

✓ Secure-deploy checklist

Correct port group (not staging) · unique identity via Customization Spec · registered + patched · enrolled in IDM · nothing unexpected listening · hardened · logged in change control. That's the enterprise standard.

SOP 04

Account Management (Manual / Break-Glass)

The by-hand way to create, lock, delete, and set up service accounts — for when you can't use IDM. Normally people come from IDM and we push keys centrally; this is the fallback every admin needs cold, plus how to build a locked-down service account (including an ACAS credentialed-scan account).

Scope: local accountsPrefer: IDMBreak-glass

▸ Prefer IDM — use these when you must

Create local accounts only for a standalone/DMZ box, when IDM is down, or for a local service/scan account that shouldn't live in IDM. Real people should come from IDM (SOP 14) so access is central and auditable.

Create a user (a person)

Create the account with a home dir and shell
useradd -m -s /bin/bash -c "Jane Doe" jdoe
-m
Make the home directory (/home/jdoe) and seed it from /etc/skel. Without it, the user has nowhere to put .ssh or configs.
-s /bin/bash
Their login shell — a real shell because a person logs in interactively.
-c "..."
The comment/full name (shows in getent passwd).
-G grp
Add to secondary groups at create time (e.g. -G wheel for sudo).
-u 1234
Force a specific UID (match across boxes if you need to).
Set a password & force a change at first login
passwd jdoe # set an initial password chage -d 0 jdoe # force them to change it at first login
Grant sudo only if they're an admin
usermod -aG wheel jdoe # wheel = sudo on RHEL (-a APPENDS, don't forget it)

✕ Never usermod -G without -a

Without -a it replaces all their groups with just that one — you can lock people out of their own groups. Always -aG.

Install their SSH key (key-based login)

The key comes from the USER, not from you. On THEIR OWN machine (laptop/workstation) they generate a key pair — the private half stays with them forever, and they hand you only the public half.

They run this on their machine:

ssh-keygen -t ed25519 -C "jdoe@laptop" # press Enter to accept the default path cat ~/.ssh/id_ed25519.pub # prints the PUBLIC key — they send you THIS one line
The line they send you looks likessh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAIB1x...long-string... jdoe@laptop

You install that public line on the box (never their private key):

mkdir -p /home/jdoe/.ssh echo "ssh-ed25519 AAAA...jdoe@laptop" >> /home/jdoe/.ssh/authorized_keys chmod 700 /home/jdoe/.ssh chmod 600 /home/jdoe/.ssh/authorized_keys chown -R jdoe:jdoe /home/jdoe/.ssh

◆ Two rules

Only the PUBLIC key (the .pub) ever leaves their machine — if someone hands you a private key, stop; that's wrong. And perms must be tight: .ssh=700, authorized_keys=600, owned by the user, or SSH silently refuses it ("permission denied (publickey)").

▸ Better: let IDM hold the key

Instead of copying keys onto every box, store the user's public key once in IDM — ipa user-mod jdoe --sshpubkey="ssh-ed25519 AAAA..." — and every enrolled client serves it automatically (SOP 14). This local method is the break-glass fallback.

Verify
id jdoe getent passwd jdoe
You'll seeuid=1002(jdoe) gid=1002(jdoe) groups=1002(jdoe),10(wheel) ← in wheel = has sudo jdoe:x:1002:1002:Jane Doe:/home/jdoe:/bin/bash ← home + real shell ✓

Sudo: how "wheel" works, and granting one user directly

See the line that makes wheel work
grep wheel /etc/sudoers
The rule that gives wheel its power%wheel ALL=(ALL) ALL ↑WHO ↑hosts ↑run-as ↑commands ( the % means "a GROUP" )

That one line is the entire reason being in wheel grants sudo. Delete it and wheel means nothing — the power lives in the file; the group is just the "who" the rule points at.

Grant ONE user directly (no group needed)

Don't edit /etc/sudoers by hand — drop a small file in /etc/sudoers.d/, always opened with visudo so it's syntax-checked (a typo in the main file can lock everyone out of sudo):

visudo -f /etc/sudoers.d/jdoe
jdoe ALL=(ALL) ALL # full sudo — prompts for THEIR OWN password
Scope it (least privilege) or skip the prompt
# only specific commands, as root (the good habit): jdoe ALL=(root) /usr/bin/systemctl restart httpd, /usr/bin/dnf # full sudo but NO password prompt (automation/service accounts): jdoe ALL=(ALL) NOPASSWD: ALL
Verify what they're actually allowed
sudo -l -U jdoe # prints exactly which sudo rules apply to jdoe

◆ Two classic gotchas

visudo sets the file to the required 0440 for you. And files in /etc/sudoers.d/ are ignored if the name has a dot or ends in ~ — name it jdoe, not jdoe.conf or a leftover backup. That's a top "why isn't my rule working?" trap.

Lock, disable, or delete an account

▸ Disable first, delete later

Locking is reversible and keeps the audit trail; deletion is permanent. In many DoD shops you disable/expire and keep the account for accountability rather than deleting it. Delete only per your retention policy.

Lock the account (reversible — keeps files)
usermod -L jdoe # lock the password (can't log in with it) chage -E 0 jdoe # expire the account (blocks all login) usermod -s /sbin/nologin jdoe # take away the shell too

Re-enable later: usermod -U jdoe, chage -E -1 jdoe, usermod -s /bin/bash jdoe.

Before deleting — see what it owns
pkill -u jdoe # stop its running processes crontab -u jdoe -l # does it have cron jobs? find / -user jdoe 2>/dev/null # files it owns (reassign or archive)
Delete (permanent)
userdel jdoe # removes the account, KEEPS the home dir userdel -r jdoe # also removes the home dir + mail spool

✕ There's no undo

userdel -r erases their home directory. Make sure nothing important lives there and no service depends on the account before you run it.

Service account — daemon type (NO login)

A service account is an identity for a program, not a person. If it only runs a local process, it must not be able to log in or hold a password. Lock it down hard:

Create it with no shell and no password
useradd -r -M -s /sbin/nologin -c "App X runtime" svc-appx
-r
System account — gets a low UID and no password aging. The right flag for daemons.
-s /sbin/nologin
No interactive shell — any login attempt is politely refused. This is the key one.
-M
No home directory (a daemon usually doesn't need one). Use -m -d /var/lib/appx instead if the service needs a home/state dir.
no password
You never run passwd on it — with no password AND nologin, it simply can't log in.
Lock the password explicitly (belt & suspenders)
passwd -l svc-appx # lock — guarantees no password login is possible
Verify it can't log in, then point the service at it
getent passwd svc-appx
The shell tells the storysvc-appx:x:987:987:App X runtime:/:/sbin/nologin ↑ nologin = no interactive login ✓

In the app's systemd unit, run it as this account: User=svc-appx. Give it ownership only of the files/dirs it truly needs — nothing more.

✓ Daemon service-account best practice

No password · /sbin/nologin · system account (-r) · least-privilege file ownership · runs under User= in its unit. If it never needs to log in, it never gets a shell.

Scan / automation account — the ACAS example (DOES log in)

Some service accounts must log in remotely — a credentialed vulnerability scanner (ACAS/Nessus) or Ansible SSHes in and runs privileged checks. This one needs a shell and elevation, so you lock it down a different way: key-only, source-restricted, scoped sudo.

Create it WITH a shell (it has to run commands)
useradd -m -s /bin/bash -c "ACAS credentialed scan" svc-acas

A real shell and a home (-m) — it logs in over SSH to run scan commands and needs somewhere for .ssh. This is the opposite of the daemon account above, on purpose.

Key-only, no password, no expiry

Where this key comes from: the scanner owns the key pair. Either ACAS/Nessus generates one in its SSH-credential settings and shows you the public key to export, or you generate a dedicated pair (ssh-keygen -t ed25519 -f acas_key), load acas_key (private) into the scanner's credential store, and put acas_key.pub (public) on each target. You only ever place the public key on the box:

# install the SCANNER's PUBLIC key (from your ACAS/Nessus SSH credential) mkdir -p /home/svc-acas/.ssh echo "ssh-ed25519 AAAA...acas_scanner_key" >> /home/svc-acas/.ssh/authorized_keys chmod 700 /home/svc-acas/.ssh; chmod 600 /home/svc-acas/.ssh/authorized_keys chown -R svc-acas:svc-acas /home/svc-acas/.ssh passwd -l svc-acas # no password login — key ONLY chage -M -1 -E -1 svc-acas # never expire (don't let it lock mid-scan)
Give it the privilege ACAS needs — scoped sudo, no prompt

Credentialed scans read protected configs, so the account elevates with sudo. It's non-interactive, so it needs NOPASSWD. Put it in its own drop-in (always edit with visudo):

visudo -f /etc/sudoers.d/svc-acas
# credentialed scanners generally need broad root read: svc-acas ALL=(root) NOPASSWD: ALL

◆ Scope it if your policy requires

NOPASSWD: ALL is effectively root — accepted for a trusted, locked-down scanner at many sites, but if your policy demands least privilege, replace ALL with the specific commands ACAS runs. Either way, protect the account hard (next step).

Restrict WHERE it can log in from

This account should only ever connect from the scanner. The clean, per-account way is to pin its key to the scanner's IP — put a from="..." in front of its authorized_keys line (edit the entry from step 2):

# /home/svc-acas/.ssh/authorized_keys — pin the key to the scanner only from="10.1.1.40" ssh-ed25519 AAAA...acas_scanner_key

Now that key works only from the scanner's IP, with no global SSH change. Optional extra layer — also limit SSH at the firewall:

firewall-cmd --permanent --add-rich-rule='rule family="ipv4" source address="10.1.1.40/32" service name="ssh" accept' firewall-cmd --reload

◆ Don't reach for AllowUsers here

The AllowUsers directive in sshd_config is a global whitelist — the moment you add it, only the users you list can log in at all, which can silently lock everyone else out. Restrict one account with from="..." on its key (above) or the firewall rule, not AllowUsers.

Utilize it in ACAS / Nessus
☞
In the scan policyCredentials → SSH → Auth method = public key → Username = svc-acas → paste its private key → Privilege escalation = sudo.

Now credentialed scans log in as svc-acas with the key and elevate via sudo to read what they need — no password anywhere, and only from the scanner.

Confirm it's working (on the target, in /var/log/secure)Accepted publickey for svc-acas from 10.1.1.40 ... ← scanner logged in ✓ sudo: svc-acas : ... COMMAND=/usr/bin/... ← elevation working ✓

✓ Login-capable service-account best practice

Key-only (password locked) · source-restricted to the scanner · scoped/NOPASSWD sudo per policy · never-expire · every login and sudo logged in /var/log/secure. A powerful account, kept on a very short leash.

◆ If the scanner's sudo fails over SSH

Check for Defaults requiretty in sudoers — it blocks non-interactive sudo (no terminal) and breaks credentialed scans. Modern RHEL 8/9 doesn't set it by default, but if a hardening baseline added it, exempt this account with Defaults:svc-acas !requiretty in its drop-in.

SOP 05

Register a RHEL Box to Satellite & Configure Repos

Point a client at your Satellite so it pulls content (packages, errata, containers) from your air-gapped Satellite instead of Red Hat directly. An activation key does most of the work; the client side is: trust it, register, then verify/enable the repos you need.

Client sideNeeds: activation key~5 min

Trust the Satellite & register

Trust the Satellite's CA (so TLS works)

Install the Satellite's CA "consumer" RPM. It adds the CA cert and repoints subscription-manager at your Satellite (rewrites /etc/rhsm/rhsm.conf):

rpm -Uvh http://satellite.example.com/pub/katello-ca-consumer-latest.noarch.rpm

◆ Do this first

Without the CA, register fails with a certificate/TLS error — same idea as the container CA trust in the RHEL manual.

Register with your activation key

The activation key (built in Satellite: Content → Activation Keys) carries the org, lifecycle environment, Content View, and which repos to enable — so one command does it all:

subscription-manager register --org="FMLBCU" --activationkey="rhel9-prod-key"
You'll seeThe system has been registered with ID: 7f3a... Installed Product Current Status: Subscribed ← good ✓
Verify it took
subscription-manager identity # org + environment it's now in subscription-manager status # 'Overall Status: Current' = good
Healthy registrationorg name: FMLBCU environment: Prod Overall Status: Current ✓

Configure repos from the client side

See which repos you have
subscription-manager repos --list | grep -E "Repo ID|Enabled" # available + on/off dnf repolist # what dnf will actually use
Enable the ones you need (if the key didn't)

A good activation key already enables BaseOS + AppStream. To turn one on by hand:

subscription-manager repos \ --enable=rhel-9-for-x86_64-baseos-rpms \ --enable=rhel-9-for-x86_64-appstream-rpms

On Satellite the labels may be your custom repo names — copy the exact Repo ID from the --list output above.

Refresh & prove it works
dnf clean all dnf makecache # pull fresh metadata from the Satellite dnf repolist # BaseOS + AppStream (+ extras) listed dnf install -y tmux # a small test install, straight from the Satellite
Successrepolist shows the enabled repos, and tmux installs from satellite.example.com ✓

▸ The newer one-liner: Global Registration

In the Satellite UI, Hosts → Register Host builds a single curl … | bash command that does CA + register + activation key in one paste. Same result — use whichever your site standardizes on.

✓ You end up with

The box pulls all packages, errata, and containers from your Satellite — and patching (SOP 07) and Leapp (SOP 06) now have content to work from.

SOP 06

In-Place UPGRADE (RHEL 8 → 9) with Leapp

A major-version jump rewrites the whole OS, so it's not a dnf update — it's Red Hat's Leapp tool, upgrading in place across a special multi-reboot. This is the runbook; rehearse it on a TEST box first (see the guided lab in the RHEL manual).

Major upgradeVia SatelliteSnapshot first

✕ Snapshot + Veeam FIRST

In-place upgrades can fail halfway. Take a vCenter snapshot and confirm a good Veeam backup so you can roll straight back.

Pre-flight

Be current on 8.x first
dnf update reboot # if the kernel updated

Leapp expects the latest 8.x minor. Update and reboot before you start (why: SOP 07).

Make sure the box can reach RHEL 9 content

The Satellite must carry RHEL 9 repos in the Content View this box uses. Confirm it's registered and current (SOP 05):

subscription-manager identity

◆ Air-gapped reality

You don't reach Red Hat — Leapp pulls the 9 packages from your Satellite's synced 9 repos. If 9 isn't synced/in the CV, there's nothing to upgrade TO.

Install Leapp
dnf install -y leapp-upgrade

Assess & fix

Run the pre-upgrade assessment
leapp preupgrade

Changes nothing — it writes a report of everything that will block you.

Clear every Inhibitor
less /var/log/leapp/leapp-report.txt

Fix each high-severity inhibitor. Common ones: third-party packages (Security Center, agents), low space on / or /boot, deprecated drivers. Some yes/no checks are cleared by answering them:

leapp answer --section check_vdo.confirm=True # example — use the ID from the report
An inhibitor in the reportRisk Factor: high (inhibitor) Title: Packages not signed by Red Hat found... → remove/replace them first

Upgrade & verify

Run it, then reboot
leapp upgrade reboot

✕ Watch via the vCenter Web Console

It reboots more than once (upgrade environment, then a SELinux relabel) and SSH drops. Right-click the VM → Launch Web Console to watch. The extra reboots are expected.

Verify you're on 9 and healthy
cat /etc/redhat-release # should say 9.x subscription-manager identity # still registered dnf repolist # repos should now be the 9 ones systemctl --failed

SOP 07

In-Place UPDATE (Minor) — and Why It's Not an Upgrade

Applying patches or moving within the same major (9.3 → 9.4) is a routine dnf update. Jumping majors (8 → 9) is a different, one-way operation (Leapp, SOP 06). This runbook does the routine update and explains the difference so you never confuse the two.

Minor / errataRoutine~15 min

Do a minor update (the routine one)

See what's waiting
dnf check-update # packages with updates available dnf updateinfo list # errata + severity — prioritize Security (RHSA)
Snapshot (prod boxes)

Quick vCenter snapshot before touching prod so you can revert if an update misbehaves. Delete it once verified.

Apply the updates
dnf update # everything dnf update --security # OR: only the security errata dnf update httpd # OR: just one package
Reboot only if needed
dnf needs-restarting -r # tells you if a reboot is required
It answers plainlyReboot is required to fully utilize these updates. → schedule one (otherwise: "No core libraries or services have been updated." → you're done)
Verify
cat /etc/redhat-release systemctl --failed

Update vs Upgrade — the difference that matters

UPDATE (minor)
Same major (9.x). Applies errata / moves 9.3→9.4. Tool: dnf update. Routine, low-risk, no special reboot.
UPGRADE (major)
Crosses majors (8→9, 9→10). Tool: Leapp (SOP 06). A project: snapshot, assess, fix inhibitors, multi-reboot. One-way.

Why you can't just "dnf upgrade" across majors

  • A major version swaps the whole userland — glibc, Python, the entire package set and ABIs. dnf can't reconcile that in one transaction; Leapp orchestrates the repo remap, package replacement, config migration, and reboots.
  • You can't skip a major. Leapp only goes N → N+1: 8→9, then 9→10. There's no 8→10 — do them in sequence.
  • Be on a recent minor first. You must be on the latest minor of the source major (e.g. 8.10) before Leapp will take you to 9.

▸ One-liner to remember

dnf update keeps you healthy within a major; Leapp is the only thing that moves you between majors. If someone says "just upgrade it," clarify which they mean.

◆ Hold a version if you must

Need to pin a package (an app that breaks on a newer build)? dnf install python3-dnf-plugin-versionlock then dnf versionlock add pkg. Use sparingly — it also holds back that package's security fixes.

SOP 16

Kubernetes: Control Plane + Workers, and Deploy an App

Stand up a small cluster (one control-plane node + two workers) with kubeadm, then deploy an app (nginx) into pods, give it CPU/memory, and expose it so people can reach it by IP. Build the control plane FIRST, then join the workers, then deploy.

3 nodeskubeadm + containerdair-gapped
Fill in — air-gapped sourcesPackages (kubeadm/kubelet/kubectl, containerd) come from [your Satellite / local mirror]; container images (nginx, the CNI, pause) come from [your internal registry]. Point the commands below at those instead of the public internet.

Prep EVERY node (control plane + both workers)

Kernel, swap, and networking prereqs
swapoff -a sed -i '/ swap / s/^/#/' /etc/fstab # keep swap off after reboot modprobe overlay && modprobe br_netfilter echo -e "overlay\nbr_netfilter" > /etc/modules-load.d/k8s.conf echo -e "net.bridge.bridge-nf-call-iptables=1\nnet.ipv4.ip_forward=1" > /etc/sysctl.d/k8s.conf sysctl --system

Kubernetes refuses to run with swap on; the bridge/forwarding sysctls let pod traffic route.

Install a container runtime (containerd)
dnf install -y containerd containerd config default > /etc/containerd/config.toml sed -i 's/SystemdCgroup = false/SystemdCgroup = true/' /etc/containerd/config.toml systemctl enable --now containerd

◆ SystemdCgroup = true

Must match kubelet's cgroup driver (systemd) or the kubelet won't start. This one line is a classic gotcha.

Install kube tools + open the firewall

The pod-network-cidr must match your CNI (10.244.0.0/16 = Flannel). When it finishes it prints a kubeadm join command — copy that, the workers need it.

Set up kubectl for your user
mkdir -p $HOME/.kube cp -i /etc/kubernetes/admin.conf $HOME/.kube/config chown $(id -u):$(id -g) $HOME/.kube/config kubectl get nodes # the control plane shows NotReady until the CNI is in (next step)

Deploy the app so people can reach it

Create the nginx deployment WITH resource allocation

A Deployment keeps the app's pods running. Set CPU/memory requests (guaranteed) and limits (ceiling) so it gets — and can't exceed — its share:

cat > nginx-app.yaml <<'YAML' apiVersion: apps/v1 kind: Deployment metadata: name: nginx spec: replicas: 2 selector: matchLabels: { app: nginx } template: metadata: labels: { app: nginx } spec: containers: - name: nginx image: registry.example.com/nginx:1.27 ports: - containerPort: 80 resources: requests: { cpu: "250m", memory: "128Mi" } limits: { cpu: "500m", memory: "256Mi" } YAML kubectl apply -f nginx-app.yaml

Give it a real IP / hostname (optional, enterprise)

MetalLB
On bare metal, gives a Service type: LoadBalancer a real IP from a pool you define — users hit a normal IP on port 80.
Ingress

✓ What you built

A 3-node cluster (1 control plane + 2 workers), nginx running in 2 pods with guaranteed CPU/memory, reachable by users through a Service. Scale it anytime: kubectl scale deployment nginx --replicas=4.

◆ Air-gapped must-dos

SOP 13

Stand Up an IDM Server (Ports + AD Trust)

Install Red Hat IDM (FreeIPA) — central identity, Kerberos, and (optionally) DNS/CA — then open exactly the right ports and establish the trust that lets Active Directory users in. Do this on a dedicated, well-named host.

ipa-serverKerberos/LDAP/CAAD trust

Install the IDM server

Prep the host (FQDN, static IP, hosts file)
hostnamectl set-hostname idm.example.com # must be a real FQDN # ensure it resolves — a line in /etc/hosts as a safety net: echo "10.1.1.10 idm.example.com idm" >> /etc/hosts

IDM is picky about identity: a proper FQDN, a static IP, and clean time sync (chrony) are prerequisites.

Install the packages
dnf install -y ipa-server ipa-server-dns freeipa-server-trust-ad

(ipa-server-dns if IDM will run DNS; freeipa-server-trust-ad for the AD trust later.)

Run the installer
ipa-server-install --setup-dns

It asks for the realm (usually EXAMPLE.COM, uppercase), domain, a Directory Manager password, and the admin password. It then sets up LDAP (389-ds), Kerberos (KDC), the CA (Dogtag), and optionally DNS — in one shot.

When it finishesSetup complete. Next steps: obtain a ticket → kinit admin Web UI: https://idm.example.com

Open the right ports (and lock the rest)

Open the IDM service ports
firewall-cmd --permanent --add-service={freeipa-4,dns,ntp} firewall-cmd --reload

The freeipa-4 firewalld service bundles the core ports. For reference, that's:

TCP 80, 443
Web UI + certificate enrollment (HTTP/HTTPS).
TCP 389, 636
LDAP / LDAPS (the directory).
TCP+UDP 88, 464
Kerberos (KDC) + kpasswd (password changes).
TCP+UDP 53
DNS (only if IDM runs DNS).
UDP 123
NTP/chrony time sync.

✕ Lock everything else

These are the only inbound ports IDM needs. Anything else listening (Section: close a port, in the RHEL manual) is attack surface — close it. Keep SSH (22) limited to admins.

Verify the server is healthy
ipactl status # every service should say RUNNING kinit admin # get a Kerberos ticket ipa user-find admin # prove the directory answers

Establish the AD trust (let AD users be recognized)

Turn on the trust controller
ipa-adtrust-install --add-sids

This adds the Samba/trust bits IDM needs to talk to AD. It also opens the need for the trust ports — add them:

firewall-cmd --permanent --add-service=freeipa-trust firewall-cmd --reload

(That adds SMB 445, NetBIOS 138/139, 135, and the global-catalog 3268/3269 needed for the AD trust.)

Create the trust to your AD domain

DNS must resolve both ways and time must be in sync between IDM and AD first. Then:

ipa trust-add --type=ad ad.example.com --admin Administrator --password
SuccessAdded Active Directory trust for realm "ad.example.com" ✓

The trust now exists. Making AD users actually able to log in on clients is SOP 15.

SOP 14

Enroll a Client Into IDM (Kerberos + Keys)

Join a RHEL box to IDM so its logins, sudo, and SSH keys all come from the central server — no more local accounts to manage. One installer does it.

Point the client's DNS at the IDM server (or ensure it can resolve it), and make sure time is synced — a skewed clock breaks Kerberos.

Install & run the client installer
dnf install -y ipa-client ipa-client-install --mkhomedir \ --server=idm.example.com --domain=example.com \ --principal admin --password
--mkhomedir
Auto-creates each user's home on first login (so IDM users don't need a pre-made dir).
--principal admin
The IDM account authorized to enroll hosts; it'll prompt for the password.

The installer configures SSSD (which talks to IDM), Kerberos, sudo, and central SSH keys — all automatically.

Verify Kerberos & central keys

Prove the client sees IDM
id ian # resolves from IDM now, not /etc/passwd kinit ian # get a Kerberos ticket as that user klist # shows the ticket
You'll seeDefault principal: ian@EXAMPLE.COM ← Kerberos working ✓
Central SSH keys — set once, work everywhere

Store the user's public key in IDM and every enrolled client serves it to sshd automatically — no per-box authorized_keys copying (that's the whole point vs. the SOP 04 manual method):

ipa user-mod ian --sshpubkey="ssh-ed25519 AAAA...ian@laptop"

Now ssh ian@any-enrolled-host works with their key, everywhere.

Grant admin centrally — not local wheel

Once a box is enrolled, stop using usermod -aG wheel on it — that's per-machine and doesn't scale. Grant sudo once in IDM and it applies to every enrolled host. Local wheel (SOP 04) becomes the break-glass fallback for when IDM is down or a box isn't enrolled.

Put admins in an IDM group
ipa group-add admins ipa group-add-member admins --users=jdoe
Make ONE IDM sudo rule for that group
ipa sudorule-add admins-sudo ipa sudorule-add-user admins-sudo --groups=admins ipa sudorule-add-host admins-sudo --hostcat=all # or scope to specific hosts ipa sudorule-mod admins-sudo --cmdcat=all # or list only specific commands

Now anyone in admins has sudo on every enrolled box. Add/remove them from the group in IDM and it changes everywhere — no touching machines.

Verify on a client
sudo -l -U jdoe # should now show the IDM sudo rule

◆ Why it "just works" on every client

When you joined the box (ipa-client-install), SSSD was set up to pull sudo rules from IDM automatically — so a rule you make on the server appears on all enrolled clients.

▸ wheel vs IDM, in one line

Local wheel = a lock on one door (per machine, break-glass). An IDM sudo rule = a master-key policy for the whole building. Once IDM owns identity, grant admin in IDM.

▸ Un-enroll (if you ever need to)

ipa-client-install --uninstall on the client, then ipa host-del web01.example.com on IDM to remove its record.

SOP 15

Let AD / Windows Users Log In

With the AD trust in place (SOP 13), make Active Directory users actually able to log into your IDM-enrolled RHEL boxes — resolve them, allow them via HBAC, grant sudo, and confirm a real login.

Needs: AD trust (SOP 13)HBAC + external groups

Confirm the trust resolves AD users

Prove an AD user is visible
ipa trust-show ad.example.com # the trust is established id aduser@ad.example.com # SSSD returns their uid/gid from AD
You'll seeuid=1670801108(aduser@ad.example.com) gid=... groups=... ← AD user resolved ✓

AD users are referenced as user@ad.example.com. If id fails, fix DNS/time between IDM and AD first.

Allow an AD group in (external → POSIX → HBAC)

Map the AD group into IDM

You don't add AD users one by one — you pull in an AD group via an IDM "external" group, then wrap it in a POSIX group IDM can use in rules:

# 1) an external group that references the AD group ipa group-add --external ad_admins_ext ipa group-add-member ad_admins_ext --external "AD\\Linux Admins" # 2) a POSIX group that contains the external one ipa group-add ad_admins ipa group-add-member ad_admins --groups=ad_admins_ext
Let that group log in (HBAC) and sudo
# HBAC rule: this group may log in (here, to all hosts via sshd) ipa hbacrule-add allow_ad_admins ipa hbacrule-add-user allow_ad_admins --groups=ad_admins ipa hbacrule-add-host allow_ad_admins --hostcat=all ipa hbacrule-add-service allow_ad_admins --hbacsvcs=sshd # sudo rule: and may run root commands ipa sudorule-add ad_admins_sudo ipa sudorule-add-user ad_admins_sudo --groups=ad_admins ipa sudorule-add-host ad_admins_sudo --hostcat=all ipa sudorule-mod ad_admins_sudo --cmdcat=all

Test a real login

Log in as the AD user from a client
ssh aduser@ad.example.com@web01.example.com # once in: id # shows AD groups + the ad_admins membership sudo -l # shows the granted sudo pwd # /home/aduser@ad.example.com — home auto-created ✓

▸ Tidy the login name (optional)

Tired of typing user@ad.example.com? On clients set use_fully_qualified_names = False and a default_domain_suffix in sssd.conf so AD users can log in as just aduser.

✓ What you achieved

AD/Windows users authenticate to RHEL with their existing AD credentials — no separate Linux accounts. Access is controlled centrally by adding/removing them from the AD group, and every login/sudo is logged.
