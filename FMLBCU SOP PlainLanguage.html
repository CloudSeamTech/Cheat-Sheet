Start Here: The Basics

This page explains the handful of words and moves that every other runbook uses — so you only learn them once. If a runbook ever loses you, come back here.

This is the plain-language edition. The shorter, expert version of every runbook lives in the main SOP binder — use whichever fits you.

The words you'll keep seeing

TerminalThe terminal is a plain window where you type instructions to the computer, one line at a time, and press Enter. No mouse — just typing. On a server you reach it two ways: through the Web Console in vCenter, or by SSH (below).
CommandA command is one line of instruction you type into the terminal. In these guides, anything in a dark box is a command. Tap Copy, paste it into the terminal, and press Enter to run it.
SSHSSH is a safe way to log in to another computer over the network from your own — like a secure remote control. You type ssh yourname@web01 and now your terminal is "inside" that other machine.
Root / sudo (being "the boss")Normal users can't make big changes — that's on purpose, so nothing breaks by accident. root is the all-powerful boss account. sudo means "do this one thing as the boss." When a runbook needs boss power, you'll become root first (next section).
Placeholder (the amber italic words)Anything shown in amber italic — like web01.example.com — is just an example. Swap in your real name, number, or address when you type it.

The moves you'll keep making

Open the terminal on a server

Two ways: In vCenter, right-click the machine → Launch Web Console (a screen opens; click into it and type). Or from your own computer's terminal, SSH in:

ssh yourname@web01.example.com

The very first time it may ask "are you sure?" — type yes and Enter.

Become the boss (root)
sudo -i

Press Enter, then type your password. The screen stays blank while you type the password — that's normal, it's hiding it. Keep typing and press Enter.

You're the boss when…the end of your prompt changes to a # symbol. (A normal user ends in $.) Type exit when you want to step back down to normal.
Run a command & read what happens

Paste the command, press Enter. Text scrolls by — that's the computer talking back. If it finishes and gives you a fresh prompt with no red "error" lines, it worked. If you see an error, read the very last line — it usually says what's wrong.

Good-to-know safety

  • Looking is safe. Commands that just show things (like ls, cat, status) can't break anything — explore freely.
  • Stop a command that's running too long or looks stuck: hold Ctrl and press C.
  • Get out of a full-screen text viewer (like a log): press q.
  • When in doubt, don't delete. Deleting is the one thing with no undo. Ask first.

Runbook 01 · plain-language

Navigate vCenter (Mission Control)

vCenter is a website where you look after all your virtual computers. This walks you in the front door and shows you what everything is.

What is a "virtual machine" (VM)?A VM is a whole computer that lives inside a bigger physical computer. One strong physical server can run many VMs at once. vCenter is where you watch and manage them all.
Open vCenter in a web browser

Open Chrome or Edge. Click the address bar at the top, type this, and press Enter:

https://vcenter-fmlbcu.example.com/ui

Type your username and password (your normal work login). You're now inside mission control.

Find the list of machines on the left

On the left is a tree — a list that opens up like folders. Click the little arrows to open each level. From top to bottom it goes:

  • vCenter → the whole system.
  • Datacenter → your site.
  • Cluster → a team of physical servers working together (yours has two).
  • Host → one physical server.
  • VM → a virtual computer running on a host.

Find the machines that are yours to look after.

Click a machine to see how it's doing

Click any VM, then click the Summary tab at the top. This is its health card. Check:

  • Is it Powered On?
  • Does it show an IP address (its phone number on the network)? If blank, a helper called VMware Tools isn't installed.
  • Any red or yellow warning triangles? Those mean "look at me."
Peek at the network (which "lane" a machine is in)
Port groupA port group is a labeled network lane. Every VM is plugged into one lane, and that lane decides which network it's on. Put a machine in the wrong lane and it can't talk to anything.
☞
Where to lookTop-left menu (three lines ☰) → Networking → open your Distributed Switch. The lanes (port groups) are listed underneath it.
Peek at storage (is there room?)
DatastoreA datastore is the hard-drive space where a VM's files live. If it fills up completely, every machine using it freezes — so free space matters.
☞
Where to look☰ menu → Storage → click a datastore → look at Free space.

The golden rules (what to do & not do)

✕ Please DON'T

Don't rename or delete port groups, the switch, or a datastore. Don't pick "Delete from Disk" on a VM (that erases it). Don't turn off a physical host without "maintenance mode." If you're unsure what a button does, don't click it — ask.

◆ DO

Look around all you want (looking is safe). Read the warning triangles first. And when you're about to change something, tell a teammate / log it.

You did it when…you can log in, find your machines in the tree, and tell whether each one is powered on, has an IP, and has any warnings.

Runbook 05 · plain-language

Give a Machine a "Library Card" (Register to Satellite)

The Satellite is like a big library that holds all the software your machines are allowed to use. Before a machine can borrow software, it needs a library card. That's what "registering" is.

Why we do thisYour machines can't reach the internet. Instead they get everything from the Satellite library. A machine with no card can't install or update anything — so this is step one for almost every new box.
Get onto the machine and become the boss

Open the terminal on the machine (Web Console, or SSH in), then become root — see The Basics:

sudo -i
Give the machine the library's ID card (so it trusts the library)

Type this one line. It downloads and installs the library's trust certificate so the machine knows the library is the real one:

rpm -Uvh http://satellite.example.com/pub/katello-ca-consumer-latest.noarch.rpm
It worked when…a couple of lines scroll by and you get a fresh prompt with no error. (If it says "certificate" errors later, this step is usually why — run it again.)
Sign up for the card using your "activation key"
Activation keyAn activation key is a pre-made signup code your team created in the Satellite. It automatically puts the machine in the right group and turns on the right software shelves — so you don't set those by hand. Ask your team for the key name.
subscription-manager register --org="FMLBCU" --activationkey="rhel9-prod-key"
You'll seeThe system has been registered with ID: 7f3a... Installed Product Current Status: Subscribed ← it has a card now ✓
Double-check the card works

These two commands ask "who am I, and am I healthy?"

subscription-manager identity subscription-manager status
Good meansorg name: FMLBCU Overall Status: Current ← healthy ✓
Prove it can borrow software

Refresh the machine's list of what's available, then install one small thing as a test:

dnf clean all dnf repolist # shows the software shelves it can now reach dnf install -y tmux # a tiny test install
You did it when…the test program installs from your Satellite (you'll see its address in the output). The machine now has its library card and can get software and updates.
Ask your teamThe exact activation key name and which org to use are set by your site. Get those two values before you start.

Runbook 07 · plain-language

Update vs Upgrade — What's the Difference?

These two words sound the same but mean very different jobs. Mixing them up is the #1 beginner confusion, so let's make it simple.

The easy way to remember itUPDATE = small touch-ups to the same version (like getting this week's fixes for RHEL 9). Easy and routine.
UPGRADE = moving to a whole new version (like RHEL 9 → RHEL 10). A big, careful project — a different runbook (06).

Do a routine update (the small, easy job)

Get on the machine and become the boss
sudo -i
See what fixes are waiting
dnf check-update # lists software with newer versions ready

If lots of lines appear, there are updates waiting. If nothing appears, you're already current — you're done.

Take a quick safety copy (for important machines)

In vCenter, right-click the VM → Snapshots → Take Snapshot. This is an "undo point" you can jump back to if an update misbehaves. (Delete it once everything's fine.)

Install the fixes
dnf update # installs everything waiting

It shows a list and asks "Is this ok?" — type y and Enter. Let it finish.

Reboot only if it tells you to
dnf needs-restarting -r
It answers plainly"Reboot is required..." → type: reboot "No core libraries...updated." → you're done, no reboot needed
You did it when…the updates installed with no errors, and you rebooted if it asked. That's a routine update — done.

Why you can't just "update" your way to a new version

People ask: "if update gets new stuff, why can't I update from RHEL 9 all the way to RHEL 10?" Here's the simple reason:

  • A new major version (9 → 10) rebuilds almost the whole operating system at once — like renovating a house down to the walls, not just repainting. The normal update tool can't safely do that.
  • A special tool called Leapp (runbook 06) does the big renovation carefully, one careful step at a time, with restarts.
  • And you can't skip: you go 8 → 9, then 9 → 10. There's no jumping straight from 8 to 10.

◆ So, in one sentence

Update keeps a machine healthy on the version it's already on. Upgrade (Leapp) is the only way to move it to the next version — and it's a planned project, not a quick command.

Runbook 09 · plain-language

Back Up a Machine With Veeam

Veeam is a program that makes safety copies of your whole machine, so if something breaks you can bring it back. This makes a copy — and then proves the copy actually works.

Backup vs snapshotA vCenter snapshot is a quick short-term "undo point" that lives on the same storage as the machine. A Veeam backup is a real, separate copy kept somewhere else — it survives even if the machine is deleted. For real safety, you want the backup.

Make the backup

Open the Veeam program

On the Veeam server (or wherever your team runs it), open the Veeam Backup & Replication console. Click Home on the left.

Start a new backup job
Backup "job"A job is just a saved recipe that says "copy THESE machines, THIS often, and keep THIS many copies." You set it up once and it can run on a schedule.
☞
Do thisHome → Backup Job → Virtual machine → VMware vSphere. Give it a clear name like Daily-Web01.
Pick the machine to copy

Click Add, browse the list from vCenter, and pick your VM. (You can pick several.)

Say where to keep it and for how long

Choose the repository (the storage where backups are kept — your team has one set up) and set how many copies to keep (for example, 14 days' worth). Click through to the end and Finish.

Run it now

Right-click your new job → Start. Watch it until it says Success (green).

◆ You may see a snapshot blink in vCenter

While Veeam copies, it briefly makes a snapshot and then removes it. Totally normal — don't worry if you see one appear and vanish.

Prove the backup actually works

Do a small test restore

A backup you've never tested isn't really a backup yet. So test it: Home → Backups → find your machine → right-click a copy → Restore guest files, and pull one file back out.

You did it when…the job shows Success, you can see a dated copy, and your test restore brought a file back. Now it's a real, trustworthy backup.

◆ The one rule to remember

A copy you've never restored is just a hope. Test-restore now and then, so you're not finding out during a real emergency.

Runbook 02 · plain-language

Make a Template From Scratch (a "Cookie Cutter")

A template is a master copy of a perfect machine — like a cookie cutter. You build one good machine once, freeze it as a stamp, and then make identical fresh copies whenever you need a new server.

Why bother?Instead of building every new server by hand (slow, and easy to get wrong), you build it perfectly one time. Every copy comes out the same — already updated, secured, and ready.

Get the Red Hat "setup disc"

Download RHEL from Red Hat's website
ISOAn ISO is the whole setup disc squished into one file — like the install CD for the operating system. You "boot" a blank machine from it to install RHEL fresh.
☞
Do this (on an internet computer — the low side)Go to access.redhat.com → log in → Downloads → Red Hat Enterprise Linux. Pick your version, then download the "Binary DVD ISO" (the full installer — not the tiny "Boot ISO" or the other formats).
Carry it across to your side
Ask your teamCopy the ISO onto your approved media, move it across the way your site allows, and put it on the share / storage your team uses. Follow every scanning/approval step.
Put the disc where vCenter can reach it
☞
Do thisIn vCenter: ☰ menu → Storage → pick a datastore → Files → Upload Files → choose the ISO.

Build the one perfect machine

Make a brand-new empty machine
☞
Do thisRight-click your cluster → New Virtual Machine → Create a new VM. Name it like a template, e.g. tmpl-rhel9-base. Guest OS = Red Hat Enterprise Linux 9. Give it CPU/memory/disk.

On the CD/DVD setting, choose Datastore ISO File, pick the ISO you uploaded, and tick Connect at power on (that's "put the setup disc in the drive").

◆ Put it on the "practice lane," not the real network

Set its network to a safe, non-production lane (a staging/management port group) for now. A brand-new, not-yet-secured machine should never touch the real network yet. The real network gets set when you make copies (Runbook 03).

Turn it on and install RHEL

Power it on, open the Web Console, and follow the on-screen installer: disk layout, a root (boss) password, an admin user, timezone. Let it finish and reboot to a login screen.

You did it when…the machine boots to a normal RHEL login prompt.
Set it up the way EVERY machine should start

Log in, become the boss, and give it your standard setup — this is what makes it "golden":

subscription-manager register --org="FMLBCU" --activationkey="rhel9-key" # library card (Runbook 05) dnf -y update # get current on updates dnf -y install open-vm-tools your-standard-tools # your usual programs

Then run your security hardening (Runbook 08). Everything you set here, every future copy will have too.

Freeze it into the cookie cutter

Wipe its "fingerprints" first
Why wipe fingerprints?Every machine has a few unique IDs. If you copy the machine without clearing them, all the copies are identical twins and they'll fight on the network. Clearing them lets each copy make its own fresh IDs on first boot.
truncate -s 0 /etc/machine-id # clear the unique machine ID rm -f /etc/ssh/ssh_host_* # clear its SSH host keys subscription-manager unregister # give back the library card (copies get their own) dnf clean all poweroff # turn it off
Turn the machine into a template
☞
Do thisRight-click the powered-off machine → Template → Convert to Template.

It now shows a template icon and can't be turned on — that's correct. You never run the cookie cutter; you stamp copies from it.

You did it when…you see tmpl-rhel9-base listed as a Template. Every new RHEL 9 server is now made from this (Runbook 03).

◆ About the template's network

Don't put a real IP address in the template — every copy would clash. The template stays on the "practice lane" with no fixed address; each copy gets its own real network and address when you deploy it (Runbook 03).

Runbook 03 · plain-language

Make a New Server From a Template

Now you stamp out a fresh copy from the cookie cutter (Runbook 02) and give it its own name and address — the safe, proper way.

Before you start

Know these four things first
  • The new machine's name (and what it's for).
  • Which network lane (port group / VLAN) it belongs on.
  • Its IP address, mask, gateway, and DNS (its network address details).
  • Which datastore (storage with room) to put it on.

If you don't have these, get them before you click — you'll be asked mid-way.

Stamp out the copy

Start a new machine from the template
☞
Do thisRight-click tmpl-rhel9-base → New VM from This Template.
Give it a name and pick its folder

Type the new server's name; choose the folder it should live in.

Pick which physical server runs it

Choose the host or cluster. If unsure, let the system place it automatically.

Pick storage with free space

Choose a datastore that has room. (The copy's disk is written here — a full datastore makes it fail.)

Pick the REAL network lane (not the practice one)

On the "Select networks" screen, choose the real production port group this server belongs on. This is where you move it off the template's practice lane.

Turn on "Customize" so it gets its OWN identity
Customization SpecA Customization Spec is a little settings sheet your team makes once. When you apply it, it stamps a unique name and IP address onto the new copy on first boot — so it's its own machine, not a clone of the master.

Tick Customize the operating system and pick the Linux spec. This is the secure, repeatable way — much better than hand-typing an IP after.

Finish and power it on

Review the summary, click Finish, then power it on. Watch it in the Recent Tasks bar at the bottom.

Check it, then bring it into the fold

Make sure it came up as its OWN machine
hostnamectl # its new name (not the template's) cat /etc/machine-id # a NEW ID ✓ ip -br a # its own IP address
Good means…a new name, a new machine-id, and its own IP — not the master's.
Register, update, join, check, secure

Get it fully set up and safe:

subscription-manager register --org="FMLBCU" --activationkey="rhel9-key" # library card dnf -y update ipa-client-install --mkhomedir --server=idm.example.com --domain=example.com # join the login server ss -tulpn # what's listening? close anything you don't expect systemctl --failed # anything broken?

Then run your hardening. Only after this is the server ready for its job.

You did it when…the new server has its own identity, a library card, is joined to the login server, has nothing odd listening, and is hardened.

Runbook 04 · plain-language

Add / Remove Accounts (People & "Robot" Accounts)

An account is like giving someone a key to the building. This shows how to make a key for a person, turn one off, and make special keys for programs (robot accounts). Normally logins come from the central login server (IDM) — this is the by-hand way for when you can't use it.

Make an account for a person

Get on the machine and become the boss
sudo -i
Create the account
useradd -m -s /bin/bash -c "Jane Doe" jdoe
What the pieces mean-m = give them their own home folder (their own space for files). -s /bin/bash = give them a command window when they log in. -c "Jane Doe" = their full name, just a label. jdoe = the short username they'll type to log in.
Give them a starting password
passwd jdoe # type a starting password (twice) chage -d 0 jdoe # make them change it the first time they log in
If they're an admin, give them "boss powers"
wheelwheel is the group of people allowed to use sudo (boss powers). Adding someone to it lets them run admin commands.
usermod -aG wheel jdoe

✕ Never leave out the -a

Type -aG (with the a), never just -G. Without the a it replaces all their groups instead of adding one — which can lock them out.

Add their SSH key (key comes from THEM)
Where the key comes fromThe person makes the key on their own computer — the private half stays with them forever; they send you only the public half. On their machine they run: ssh-keygen -t ed25519, then cat ~/.ssh/id_ed25519.pub, and send you that one line.

You paste their public line onto this machine (never their private key):

mkdir -p /home/jdoe/.ssh echo "ssh-ed25519 AAAA...jdoe@laptop" >> /home/jdoe/.ssh/authorized_keys chmod 700 /home/jdoe/.ssh chmod 600 /home/jdoe/.ssh/authorized_keys chown -R jdoe:jdoe /home/jdoe/.ssh

◆ Two quick rules

Only the public key (the .pub one) ever leaves their computer — if anyone hands you a private key, stop. And those chmod lines matter: get the folder/file permissions wrong and SSH quietly refuses the key.

Check it worked
id jdoe
You'll seeuid=1002(jdoe) ... groups=1002(jdoe),10(wheel) ← "wheel" means they got boss powers ✓

How "wheel" gives boss powers (and giving just one person)

The ideaBeing in the wheel group gives boss powers because of ONE line in a settings file (/etc/sudoers) that says "everyone in wheel is allowed." The group is the guest list; that line is the rule that lets the list in.
See the rule
grep wheel /etc/sudoers
The one line that matters%wheel ALL=(ALL) ALL ↑ the "%" means the GROUP wheel; the rest means "can run anything"
Give boss powers to ONE person (without the group)

Make a little rule file just for them. Always open it with visudo — it checks your typing, so a mistake can't lock everyone out:

visudo -f /etc/sudoers.d/jdoe

Put one line inside it:

jdoe ALL=(ALL) ALL # this person can now use sudo
Check itsudo -l -U jdoe shows exactly what they're allowed to do.

◆ Little gotcha

Name the file plainly (jdoe) — Linux ignores rule files whose name has a dot or ends in ~. That's a common "why isn't it working?" surprise.

Turn off or delete an account

◆ Turn off first, delete later

Turning off is like deactivating a key card — reversible, and it keeps a record. Deleting is permanent. Most places turn off and keep the account for a while before deleting.

Turn it off (reversible)
usermod -L jdoe # lock the password chage -E 0 jdoe # mark the account expired (blocks login) usermod -s /sbin/nologin jdoe # take away the command window

To turn it back on later: usermod -U jdoe, chage -E -1 jdoe, usermod -s /bin/bash jdoe.

Delete it (permanent — no undo)
userdel jdoe # removes the account, KEEPS their home folder userdel -r jdoe # ALSO deletes their home folder

✕ Careful

userdel -r erases their files with no undo. Make sure nothing important is in their folder first.

Robot account #1 — never logs in (for a program)

What's a service account?A service account is a key for a program, not a person. If the program just runs quietly on the box, its account should never be able to log in and should have no password.
Make it with no login and no password
useradd -r -M -s /sbin/nologin -c "App X runtime" svc-appx passwd -l svc-appx # lock the password so it truly can't log in
The pieces-r = a "system" account (for programs). -s /sbin/nologin = no command window — can't log in. -M = no home folder needed. No password is ever set.
Check itgetent passwd svc-appx should end in /sbin/nologin. The program runs as this account; nobody logs in as it.

Robot account #2 — DOES log in (like the security scanner)

Why this one is differentSome robots have to log in to each machine to do their job — the security scanner (ACAS/Nessus) logs into every box to check it. So this account needs a command window. We keep it safe a different way: key-only, locked to the scanner, and given just the power it needs.
Make it WITH a command window
useradd -m -s /bin/bash -c "ACAS scan account" svc-acas
Key only, no password, never expires

The scanner owns the key. You put its public key here, then lock the password so only the key works:

mkdir -p /home/svc-acas/.ssh echo "ssh-ed25519 AAAA...scanner_key" >> /home/svc-acas/.ssh/authorized_keys chmod 700 /home/svc-acas/.ssh; chmod 600 /home/svc-acas/.ssh/authorized_keys chown -R svc-acas:svc-acas /home/svc-acas/.ssh passwd -l svc-acas # key only, no password chage -M -1 -E -1 svc-acas # never expire (don't lock it mid-scan)
Give it the boss power it needs to scan

Credentialed scans need to read protected files, so it uses sudo. Because it runs on its own (no human to type a password), add a "no-password sudo" rule — always edit with visudo:

visudo -f /etc/sudoers.d/svc-acas
svc-acas ALL=(root) NOPASSWD: ALL
Lock it to the scanner only

Pin its key so it only works from the scanner's address — add from="..." in front of its key line:

# in /home/svc-acas/.ssh/authorized_keys from="10.1.1.40" ssh-ed25519 AAAA...scanner_key
You did it when…the scanner can log in as svc-acas using its key (only from its own address) and run its checks. In the scanner (ACAS/Nessus) settings, set SSH → public key → username svc-acas → escalation sudo.

◆ Doing 40 machines? Don't do it by hand.

This account has to exist on every machine the scanner checks — but you push it to all of them at once with Ansible (Runbook 12), or bake it into your template (Runbook 02) so new machines already have it. Never repeat these steps 40 times.

Runbook 06 · plain-language

Big Upgrade (RHEL 8 → 9) With Leapp

A big upgrade moves a machine to a whole new version. Think of it like renovating a house down to the walls — not just repainting. Because it's a big job, you build safety nets first, then let a special tool do the renovation carefully.

LeappLeapp is Red Hat's renovation tool. It does the whole version change in careful steps, with restarts. You never do a big upgrade with the normal update command — only Leapp.

✕ Practice on a test machine first

Never do your first-ever Leapp on a machine people rely on. Try it on a spare/test box, and always make the safety nets in step 1.

Build safety nets, then get ready

Make TWO safety nets first

In vCenter, right-click the machine → Snapshots → Take Snapshot (a quick "undo point"). Also make sure it has a good Veeam backup (Runbook 09). If the renovation goes wrong, these bring it back.

Why both?A snapshot is a fast undo, but it lives on the same storage. A Veeam backup is a separate, real copy. Two nets = you're safe even if one fails.
Get fully current on version 8 first

Become the boss, update everything, and reboot. (You can't renovate a run-down house — bring it up to date first.)

sudo -i dnf update reboot # if the update changed the core
Make sure it can reach the new version's software

The machine gets the version-9 software from your Satellite library. Confirm it still has its library card (Runbook 05):

subscription-manager identity
Ask your teamThe Satellite must actually have RHEL 9 software loaded for this machine's group. If it only has version 8, the upgrade has nothing to move to — check with whoever runs the Satellite.
Install the renovation tool
dnf install -y leapp-upgrade

Check, fix, then renovate

Run the "check first" — it changes nothing
leapp preupgrade

This just inspects the machine and writes a to-do list of anything that would block the upgrade. Nothing is changed yet.

Read the list and fix every "inhibitor"
InhibitorAn inhibitor is a hard blocker — a problem you must fix before the upgrade will run. Common ones: leftover non–Red Hat programs, or not enough free disk space.
less /var/log/leapp/leapp-report.txt # press q to quit the viewer

◆ The usual culprit

Extra programs from other vendors (like a security appliance) are the #1 blocker. Sometimes the cleaner path is to build a fresh version-9 machine (Runbook 02/03) and reinstall the app, instead of fighting the blockers.

Do the upgrade, then reboot
leapp upgrade reboot

✕ Watch it in the vCenter Web Console

The machine will reboot more than once and your SSH connection will drop — that's expected, don't panic. Open the machine's Web Console in vCenter to watch it work through the renovation.

Check it landed on version 9
cat /etc/redhat-release # should now say 9.x systemctl --failed # nothing broken?
You did it when…it says release 9.x and shows "0 loaded units" (nothing failed). Then run a normal update and test your app. If it went wrong — jump back with the snapshot or Veeam.

Runbook 08 · plain-language

Security Scan → Harden a Machine (STIG)

A STIG is a security checklist — like a home inspection that checks every lock and alarm. First you scan (find what's unlocked), then you harden (lock it down), then you save the report for your security officer.

The wordsSTIG = the official security checklist. SCAP / OpenSCAP = the tool that checks the machine against the checklist automatically. Finding = something on the list that failed and needs fixing. ISSO = your security officer, who wants the results.

Scan (find what's unlocked)

Install the scanner and the checklist
sudo -i dnf install -y openscap-scanner scap-security-guide
Run the scan (it makes a report you can read)
mkdir -p /var/log/compliance oscap xccdf eval \ --profile xccdf_org.ssgproject.content_profile_stig \ --results /var/log/compliance/stig-results.xml \ --report /var/log/compliance/stig-report.html \ /usr/share/xml/scap/ssg/content/ssg-rhel9-ds.xml

Open the stig-report.html file in a web browser. Each item is pass or fail, grouped by how serious it is. The fails are your to-do list.

Harden (lock it down) — carefully

Snapshot first, then get the auto-fix list

Take a vCenter snapshot (undo point). Then have the tool write a fix-it playbook from the same checklist:

oscap xccdf generate fix \ --profile xccdf_org.ssgproject.content_profile_stig \ --fix-type ansible \ /usr/share/xml/scap/ssg/content/ssg-rhel9-ds.xml > stig-remediate.yml
Apply a few fixes, then scan again

Ansible: Do a Task on Many Machines at Once

Ansible is like a universal remote control: from one spot, it does the same job on 5 or 500 machines at once. There's nothing to install on the machines — it just uses SSH to reach them.

The three piecesInventory = a phone book listing the machines. Playbook = a recipe of steps written in a simple text file. Run = you tell Ansible to follow the recipe on the machines in the phone book.

Set it up

Install Ansible on your control machine

You install it in one place — the machine you'll drive from, not the targets:

sudo dnf install -y ansible-core
Make the phone book (inventory)

Make a file called inventory.ini. The names in brackets are groups; list the machines under them:

[web] web01.example.com web02.example.com
Check you can reach them

Green = good (one line per machine)web01.example.com | SUCCESS => { "ping": "pong" }

Write & run a "patch everything" recipe

Write the recipe (playbook)

Make a file patch-reboot.yml. Spacing matters — use 2 spaces, never Tabs:

--- - name: Update and reboot if needed hosts: all # which machines (from the phone book) become: yes # use boss powers (sudo) tasks: # the list of steps - name: Update everything ansible.builtin.dnf: name: "*" state: latest - name: Reboot only if it's needed ansible.builtin.reboot: when: ansible_reboot_pending | default(false)

Quick people-jobs across all machines

Runbook 13 · plain-language

Build an IDM (Login) Server

IDM is like a central security desk for the whole building. Instead of every machine keeping its own list of who's allowed, they all ask one desk: "is this person allowed, and what can they do?" This builds that desk.

The wordsIDM = the central login server (also called FreeIPA). Directory = its list of all the people. Kerberos = its ticket system (when you log in, it hands you a "ticket" that proves who you are). Realm = the name of your login area, usually your domain in capital letters (like EXAMPLE.COM).

Build the desk

Prep the machine (name, address, clock)

IDM is fussy: it needs a proper full name, a fixed IP, and a correct clock. Become the boss, then:

hostnamectl set-hostname idm.example.com # a real full name echo "10.1.1.10 idm.example.com idm" >> /etc/hosts # help it find itself
Install the software
dnf install -y ipa-server ipa-server-dns freeipa-server-trust-ad

(The last two add DNS and the ability to trust Windows/AD later.)

Run the installer
ipa-server-install --setup-dns

It asks a few questions: your realm (like EXAMPLE.COM), your domain, and two passwords (a master "Directory Manager" one and the admin one). Then it builds everything — the people list, the ticket system, and the certificate authority — by itself.

You did it when…it says "Setup complete" and gives you a web address like https://idm.example.com.

Open the right doors, lock the rest

Open the doors (ports) IDM needs
firewall-cmd --permanent --add-service={freeipa-4,dns,ntp} firewall-cmd --reload

DNS (53) = the phone book (if IDM runs it). time (123) = the clock. Those are the only doors it needs — everything else stays shut.

✕ Lock the rest

Don't leave other doors open. If ss -tulpn shows something listening that isn't on that list, close it. Keep SSH (door 22) for admins only.

Check the desk is open and working

Let Windows (AD) users be recognized

Shake hands with the Windows domain

ipa trust-add --type=ad ad.example.com --admin Administrator --password
You did it when…it says the trust was added. The two desks now recognize each other. Making Windows users actually able to log in is Runbook 15.

Runbook 16 · plain-language

Kubernetes: Run an App in Pods

Kubernetes is like a team manager for apps. You tell it "keep 2 copies of this app running and let people reach it," and it makes that happen and keeps it healthy. You build a manager machine, add worker machines, then hand it an app.

The words, in plain termsContainer = a lunchbox with one app already packed inside, ready to run anywhere. Pod = one running copy of your app. Node = a machine in the team. Control plane = the manager/brain that decides what runs where. Worker = a machine that actually runs the app copies. Deployment = your instruction "keep N copies running." Service = a stable doorway so people can reach the app even as copies come and go.
Ask your team (air-gapped)Since you can't reach the internet, the software (kubeadm, containerd) comes from your Satellite/mirror and the app "lunchboxes" (images) come from your internal registry. Point the commands at those.

Architecture Q&A — the important questions, answered simply

These are the classic "explain Kubernetes" questions. Here's each one in plain words, using the same team-manager picture. (First, the quick cast: control plane = the brain/manager; worker nodes = the players that run apps; container = a lunchbox with one app inside; pod = one running app copy.)

1 · Explain the Kubernetes architecture (the big picture)

Kubernetes has two kinds of machines. The control plane is the brain that makes all the decisions, and the worker nodes are the muscle that actually run your apps. The brain has a few helpers (API server, etcd, scheduler, controller manager) and each worker has a few helpers (kubelet, kube-proxy, container runtime). Together they keep your apps running exactly the way you asked.

2 · What is the role of the Control Plane?

The control plane is the manager/brain. It takes your orders ("keep 2 copies of this app running"), decides which worker should run each copy, and constantly checks that what's happening matches what you asked. If a copy dies, it arranges a new one. It usually doesn't run your apps itself — it directs the workers.

3 · What are Worker Nodes and their components?

Worker nodes are the machines that actually run your apps (the players). Each has three helpers: the kubelet (the team captain that talks to the brain and starts/stops apps on that machine), the container runtime (the hands that open and run the app lunchboxes), and kube-proxy (the traffic director that gets network messages to the right app).

4 · How does the API Server work?

The API server is the front desk of the brain. Everything talks through it — you, the other brain helpers, and the workers. When you say "run this app," the request goes to the API server; it checks you're allowed, writes it down in etcd, and passes it along. Nothing happens in the cluster without going through the front desk.

5 · What is etcd, and why is it important?

etcd is the cluster's notebook — it writes down everything: what should be running, what is running, and all the settings. It matters because it's the single source of truth. If etcd is lost, the cluster forgets everything about itself — which is exactly why you back it up carefully.

6 · How does the Scheduler work?

The scheduler is the seating host at a restaurant. When a new app copy needs to run, it looks at all the workers, sees which have enough room (CPU/memory) and fit the rules, and picks the best worker to place it on. It decides where a copy runs — not how.

7 · What is the role of the Controller Manager?

The controller manager is the safety inspector that never sleeps. It constantly compares "what you asked for" with "what's really happening." Asked for 2 copies but only 1 is up? It starts another. A worker went down? It notices and reacts. It's the watchdog that keeps reality matching your wishes.

8 · How does Kube-proxy work?

Kube-proxy is the traffic director on each worker. App copies come and go and change addresses, so kube-proxy keeps a live map and makes sure that when someone contacts the app's stable "doorway" (the Service), the message is forwarded to a healthy copy. It handles the network plumbing so you never chase moving addresses.

9 · What is the role of the Container Runtime?

The container runtime is the hands that actually open and run the lunchboxes (containers). Kubernetes decides what should run; the runtime (like containerd) does the real work — downloading the app image and starting it on the worker. No runtime, and nothing actually runs.

10 · How do all the components work together?

Here's the whole story in one example. You tell the API server "run 2 copies of my app." It saves that in etcd. The scheduler picks which workers will run them. On each chosen worker, the kubelet tells the container runtime to start the app, and kube-proxy wires up the network so people can reach it. The controller manager keeps watching — if a copy dies, it notices and the cycle repeats to bring it back. In short: the brain decides, the workers do, and it heals itself.

Get all 3 machines ready (the manager + 2 workers)

Turn off swap and set a few network switches

Run this on every machine (become the boss first). Kubernetes refuses to run with "swap" on, and these settings let app traffic flow:

swapoff -a sed -i '/ swap / s/^/#/' /etc/fstab modprobe overlay && modprobe br_netfilter echo -e "overlay\nbr_netfilter" > /etc/modules-load.d/k8s.conf echo -e "net.bridge.bridge-nf-call-iptables=1\nnet.ipv4.ip_forward=1" > /etc/sysctl.d/k8s.conf sysctl --system

Add a New Disk & Make It Stick (Filesystems / fstab)

A brand-new blank disk is like an empty room with no door. To use it you do three things: put a floor in it (format), add a door from a hallway (mount it to a folder), and write it on the building map so the door opens by itself every day (fstab).

The wordsFormat = put a filesystem on a blank disk so it can hold files (like laying a floor). Mount = make the disk show up as a folder you can use. /etc/fstab = the machine's "building map" that lists which disks mount to which folders at startup.
First, give the VM a new disk in vSphere

If the disk isn't there yet, add it from vSphere (the space comes from the shared datastore):

☞
In vCenterRight-click the VM → Edit Settings → Add New Device → Hard Disk → set the size → OK. (Make sure the datastore has room.)

The VM now has the disk, but Linux won't see it until you tell it to look — that's the very next step.

Find the new disk and put a "floor" in it

Become the boss. List the disks to find the new empty one (it has no mount folder yet), then format it:

# make Linux notice the disk vSphere just added: for h in /sys/class/scsi_host/host*/scan; do echo "- - -" > "$h"; done lsblk # find the new disk, e.g. sdb mkfs.xfs /dev/sdb1 # put a filesystem on it (XFS is the RHEL default)

✕ Formatting erases everything

Only format a truly new, empty disk — it wipes anything on it. Check the name with lsblk twice before you format.

Make a folder and connect (mount) the disk to it
mkdir -p /data # an empty folder to use as the "door" mount /dev/sdb1 /data # the disk now shows up as /data df -h /data # confirm it's there and shows the space
Heads up: this is temporaryA plain mount lasts only until the next reboot. Step 3 makes it come back automatically.
Write it on the "building map" so it comes back every reboot

First get the disk's UUID — its permanent name tag (better than /dev/sdb1, which can change):

blkid /dev/sdb1 # copy the UUID="..." part

Then add ONE line to /etc/fstab. Each line has six little parts:

UUID=a1b2c3d4-.... /data xfs defaults 0 0
The six parts, left to right① which disk (the UUID) · ② which folder (/data) · ③ type (xfs) · ④ options (defaults; add nofail for a non-critical disk) · ⑤ backup flag (leave 0) · ⑥ boot-check order (0 for a data disk).
Test it BEFORE you reboot (very important)
mount -a # tries the whole map right now. NO error = your line is good. findmnt /data # confirms it's mounted

✕ Why this test matters so much

A wrong line in /etc/fstab can stop the machine from booting (it gets stuck in "emergency mode"). Running mount -a checks your line while the machine is still up, so you catch a mistake before a reboot — not after, when it's much harder to fix.

You did it when…mount -a gives no error and df -h shows your new space on /data. It'll now come back on its own after every reboot.

◆ If a bad fstab already froze a boot

At the emergency screen: log in, type mount -o remount,rw / (makes the system editable), fix or delete the bad line in /etc/fstab, then reboot. That's the way back.

Container Fix-It: "What's Wrong With My Container?"

The everyday "my container is misbehaving" problems, and the simple fixes. These use Docker (the most common tool for running a single container by hand). The same ideas apply to Kubernetes pods — where it helps, there's an "In Kubernetes" note.

Quick reminderA container is one running copy of an app — a "lunchbox" that's open and running. An image is the recipe/lunchbox it was made from. Docker runs one container at a time by hand; Kubernetes is the manager that runs lots of them for you.

1 · A container starts, then immediately quits. How do I find out why?

It tried to run, hit a problem, and gave up. To find out why, look at what it said and how it exited. Work down this list — the first one usually tells you.

docker logs <container_id> # its last words — the error is usually here docker ps -a # its status + exit code (-a shows stopped ones too) docker inspect <container_id> # all its settings and details docker run -it --entrypoint /bin/sh <image_name> # go INSIDE and poke around by hand
In KubernetesSame idea: kubectl logs <pod> for its last words, and kubectl describe pod <pod> for why it won't start.

2 · My app in a container can't reach the database on the host machine. Why?

Inside a container, "localhost" means the container itself — not the computer it's running on. So when your app looks for the database at "localhost," it's searching inside its own little box and finding nothing. To reach the real host machine, use the special name host.docker.internal instead.

# point the app's database setting at the host: DB_HOST=host.docker.internal # on Linux, also add this when you run the container: docker run --add-host=host.docker.internal:host-gateway <image_name>

3 · The container is running, but I can't open the app in my browser.

The app is up but the door to it isn't open. Check these four things:

  • The app must listen on 0.0.0.0 (all doors), not 127.0.0.1 (which means "only talk to myself"). If it only listens to itself, no one outside can reach it.
  • Check the port mapping with docker ps — it shows which outside port connects to which inside port.
  • Make sure you published the port when you started it: -p <host_port>:<container_port>.
  • Make sure a firewall (or a cloud "security group") isn't blocking that port.

4 · I need the data to survive even if the container is deleted. How?

By default, when you throw a container away, its files go with it. To keep the data, put it in a Volume — a storage box that lives outside the container and sticks around.

docker volume create mydata docker run -v mydata:/app/data <image_name> # files in /app/data now survive
In KubernetesSame idea, called a PersistentVolume — storage that outlives the pod.

5 · My image (the app's lunchbox recipe) is huge. How do I shrink it?

A big image is slow to move and store. Trim it like this:

  • Start from a tiny base (like alpine, a very small Linux).
  • Add a .dockerignore file to leave out junk you don't need.
  • Combine RUN steps so there are fewer layers.
  • Remove leftover packages and cache.
  • Use a multi-stage build — build in a big workshop, then copy only the finished result into a tiny final image:
# stage 1: the big workshop that builds the app FROM node:18 AS build WORKDIR /app COPY . . RUN npm install && npm run build # stage 2: a tiny final image with ONLY the finished files FROM nginx:alpine COPY --from=build /app/dist /usr/share/nginx/html EXPOSE 80

6 · Two containers need to talk to each other. How?

Put them on the same private network, and then they can find each other by name — no chasing IP addresses.

docker network create mynet docker run --network mynet --name app1 <image1> docker run --network mynet --name app2 <image2> # now app1 can reach app2 just by using the name "app2"
In KubernetesPods reach each other through a Service by name automatically — same idea, built in.

7 · How do I limit how much CPU and memory a container can use?

Give it a cap when you start it, so one container can't hog the whole machine:

docker run -d --cpus="1.0" --memory="512m" <image_name> # at most 1 CPU + 512 MB
In KubernetesSame idea, set as requests and limits in the pod — exactly like the app file in the Kubernetes tab.
The pattern behind all of theseWhen a container misbehaves: read its logs first, check where it's listening and which ports are open, remember "localhost" means the container itself, and use volumes so data isn't lost. Those few habits solve most container problems.

Zip & Unzip Files (Tarballs)

On Windows you right-click a folder and pick "Send to → Compressed (zipped) folder" to squish a bunch of files into one small file. Linux does the exact same thing — you just type it. Here's how, and why you'd bother.

Why zip at all? (same reasons as Windows)1) Bundle — put many files/folders into ONE file, so it's easy to move, email, or carry across the air gap on a disc. 2) Shrink — make it smaller so it takes less space and transfers faster (a text log can shrink 80–90%). Also handy for keeping a backup copy of a folder before you change it.

The Linux way: tar (the "box")

What "tar" istar packs many files into one file — a "tarball." By itself it just bundles (doesn't shrink). Add the z to also vacuum-seal it. The result is a .tar.gz file — a packed and shrunk box.
Zip a folder into one small file
tar czf backup.tar.gz myfolder # bundle + shrink 'myfolder' into backup.tar.gz
The letters, decodedc = Create (make one) · z = zip/shrink it · f = the Filename to make. Read it as "create a zipped file."
Peek inside without unpacking
tar tzf backup.tar.gz # t = lisT what's inside (just looking)
Unzip it (get the files back out)
tar xzf backup.tar.gz # x = eXtract (unpack it here)
Remember just three lettersc = Create · x = eXtract · t = lisT. Keep z (shrink) and f (file) on all of them.

Other handy ways

Shrink just ONE file
gzip bigfile.log # becomes bigfile.log.gz (the original is replaced) gunzip bigfile.log.gz # turn it back into bigfile.log
Make a Windows-style .zip (to share with Windows folks)
zip -r archive.zip myfolder # -r = include everything in the folder unzip archive.zip # unpack a .zip
Which one to use?Staying on Linux? Use tar (.tar.gz) — it's the native way. Sending to a Windows person? Use zip — they can open it with a double-click.

◆ A great real use: free up space WITHOUT losing anything

Disk getting full from old logs? Instead of deleting them, shrink them — gzip a big log and it keeps the data but reclaims most of the space. In a compliance shop where you must keep logs, that's the right move (delete is the last resort).

You did it when…you can make a .tar.gz from a folder, peek inside it, and unpack it again — and you know to reach for zip when sharing with Windows.

Build a STIG'd RHEL 9 Box (from the Installer)

"STIG'd" means the box is locked down to the military's security checklist (DISA STIG). A big part of that is set up during the install — before the box even boots. Two things matter most: (1) tell the installer to apply the STIG, and (2) put certain folders on their own separate storage. Here's the whole thing, step by step.

The wordsSTIG = the DISA security checklist. Security Policy = a screen in the installer where you pick that checklist so it's applied for you. Partition = a separate slice of the disk. Some folders must live on their own slice.

Start the installer

Boot the RHEL 9 install disc

In vSphere, attach the RHEL 9 ISO to a new VM and power it on (making the VM is Runbook 02). Open the Web Console to watch, pick your language, and you land on the big menu screen — the Installation Summary. This hub is the "tools menu" where you set everything before installing.

Turn on the STIG security profile

Open Security Policy and pick the STIG
☞
On the hubClick Security Policy → in the list choose "DISA STIG for Red Hat Enterprise Linux 9" → Select profile → Done.

This tells the installer to lock the box down to the STIG and to check your setup as you go. If your storage doesn't meet the STIG, it shows a yellow warning — that's your cue for the next step.

Give certain folders their OWN storage (separate partitions)

Why separate them? (two simple reasons)1) Contain the mess — if one folder fills up (logs are the usual one), it can't fill up and crash the WHOLE box; the flood stays in its own room. 2) Its own rules — each room can have safety rules (like "no running programs from /tmp"), which the STIG requires.
Open the disk setup and choose custom
☞
On the hubInstallation Destination → pick your disk → choose Custom (or "I will configure partitioning") → Done. Set the type to LVM.
Make a separate slice for each of these

The STIG requires each of these on its own partition/volume:

  • / — the main system
  • /boot — starts the machine (a plain partition, ~1 GB)
  • swap — spillover memory
  • /home — people's files
  • /var — changing system data
  • /var/log — the logs
  • /var/log/audit — the security audit logs (auditors REALLY check for this one)
  • /var/tmp — temporary files
  • /tmp — temporary files

If the Security Policy still shows a warning after this, it's telling you a required folder isn't separate yet — add it. Then accept the changes and Done.

You did it when…the Security Policy warning about partitions clears (no more yellow "not compliant" note about mount points).

Finish the install

Set the root password and make your admin user

On the hub, set the Root password and create your admin user. The STIG has strict password rules — use a long, strong one or it'll complain.

Begin the installation

Click Begin Installation. It installs the system and applies the STIG lockdown as it goes. Reboot when it's finished.

After it boots, check the STIG actually took
sudo -i oscap xccdf eval --profile xccdf_org.ssgproject.content_profile_stig \ --report /root/stig.html \ /usr/share/xml/scap/ssg/content/ssg-rhel9-ds.xml

Open /root/stig.html in a browser to see pass/fail. (Full scanning/hardening is Runbook 08.)

Connect the new box to your Satellite (so it can get updates)

WhyA brand-new box can't get updates until it's connected to your Satellite — the library that hands out approved software (Runbook 05). Your boss is right: the Satellite can make a ready-made link (a command) you paste on the box to connect it in one shot.
Get the link from Satellite
☞
In the Satellite web pageHosts → Register Host → pick the group/environment and an activation key → it builds a one-line command (a curl … | bash). Copy it.
Make sure the box can REACH the Satellite

The box has to be on a network that can talk to the Satellite server (same network or a routable one, and able to look up its name). If it can't reach it, the paste command just hangs/times out. (This is the "same network" part your boss mentioned.)

Paste the command on the new box
# the exact link comes from Satellite — this is the shape of it: curl -sS "https://satellite.example.com/register?activation_keys=rhel9-key&..." | bash

That one command trusts the Satellite, registers the box, and turns on its software shelves — all at once.

Check it, then update
subscription-manager status # want: Overall Status: Current dnf repolist # the shelves it can now reach dnf -y update # it can finally get updates ✓
DoneThe STIG'd box is built, locked down, connected to the Satellite, and updating. This is your golden-image starting point (turn it into a template with Runbook 02's freeze step).

◆ On RHEL 10

The installer works the same way — Security Policy + separate partitions. Just confirm a "DISA STIG for RHEL 10" profile is actually in your installer/content before relying on it (the RHEL 10 STIG is newer). Everything else here is the same idea.
